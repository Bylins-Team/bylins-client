# Панели вывода: архитектура, модель скролла, выделение, поиск

Это исчерпывающее описание подсистемы вкладки **«Вывод»** — кастомного
split-scrollback компонента с собственным выделением и поиском. Раздел
[«Подводные камни»](#подводные-камни) — самое важное: там собраны грабли, на
которые ушли месяцы. Если меняешь скролл/выделение — **сначала прочитай его**.

См. также: [TABS_DESIGN.md](TABS_DESIGN.md) (маршрутизация текста по вкладкам),
[../ARCHITECTURE.md](../ARCHITECTURE.md) (общий обзор проекта).

---

## 1. Что это и как ведёт себя

Вкладка «Вывод» содержит внутренние под-вкладки (Главная/Логи/Чат/плагинные).
Каждая показывает свой буфер текста MUD-сервера. Поведение:

- **Внизу** — одно окно, автоскролл за новым текстом (follow).
- **Скролл вверх** → окно делится: верх — скроллбэк (заякорен), низ — живой
  хвост (всегда показывает конец лога). Между ними перетаскиваемый разделитель.
- Докрутка вниз до непрерывности → схлопывается в одно окно (бесшовно).
- **Позиция держится** при дописывании снизу, смене высоты окна, переключении
  вкладок; «плетётся» к началу при вытеснении строк из буфера.
- **Выделение** мышью по всему буферу (даже «через разрыв» панелей), переживает
  раздвоение/схлопывание, Ctrl+C / Ctrl+Insert / Ctrl+A.
- **Поиск** (Ctrl+F): подсветка всех совпадений + текущего, навигация, regex.
- Скроллбар интерактивный (тянется за любую точку). Разделитель — свой на вкладку.

## 2. Слои и почему так

Три слоя, осознанно разделённые:

| Слой | Где | Зависит от Compose | Тестируется юнитами |
|------|-----|:--:|:--:|
| **Чистая логика** | `ui/scroll/` | нет | да |
| **Состояние вкладки** | `OutputViewHolder` | да (snapshot-state) | нет |
| **Рендер + ввод (desktop)** | `ui/components/output/` | да | нет (пиксельная склейка) |

Главная идея: **вся логика, которую можно проверить без экрана, вынесена в
`ui/scroll/` и покрыта тестами.** Почти все баги этой подсистемы сидели НЕ в
логике, а в Compose-склейке (рекомпозиция, жесты, измерения) — её юнит-тестами
не покрыть, поэтому она максимально тонкая, а грабли задокументированы ниже.

### Карта файлов

```
ui/scroll/                         (чистый Kotlin, без Compose — тестируемо)
  OutputBuffer.kt        ContentSnapshot(text, firstSeq, lineCount), BufferGeometry
  OutputScrollController.kt  follow/anchor/split: решает Bottom | ToLine(seq) | None
  BufferOffsets.kt       seq↔строка↔столбец↔char-offset
  OutputSelection.kt     выделение по (seq,col) всего буфера
  OutputSearch.kt        поиск (подстрока/regex), навигация по совпадениям
  LineStack.kt           стопка строк: высоты → вертикальные позиции, поиск строки по y
  LineLayoutCache.kt     разметка по строкам: переиспользование неизменившихся

ui/components/output/               (Compose desktop)
  OutputViewHolder.kt    долгоживущее состояние ОДНОЙ вкладки (в ClientState)
  ScrollbackOutputCore.kt  портируемое ядро: маппинг seq↔px по строкам, OutputCanvas, OutputScrollbar
  DesktopOutputInput.kt  главный composable ScrollbackOutputView: измерение, ввод, рендер
  OutputSearchBar.kt     строка поиска (Ctrl+F)

ui/components/OutputPanel.kt        под-вкладки + выбор источника снимка
tabs/Tab.kt, TabManager.kt          буферы вкладок (seq), маршрутизация
network/TelnetClient.kt             буфер главной вкладки (receivedData + seq)
```

Тесты: `src/test/.../ui/scroll/` — `OutputScrollControllerTest`, `BufferOffsetsTest`,
`OutputSelectionTest`, `OutputSearchTest`; плюс seq-тесты в `tabs/TabTest`.

## 3. Модель буфера и нумерация строк (seq)

Скролл/выделение/поиск опираются на **абсолютный порядковый номер строки `seq`**,
а не на пиксели и не на индекс в текущем буфере. `seq` монотонен и переживает
вытеснение строк (скользящее окно).

`ContentSnapshot(text, firstSeq, lineCount)`:
- `firstSeq` — сколько строк уже вытеснено сверху (= seq верхней строки буфера);
- строка с индексом `i` в буфере имеет `seq = firstSeq + i`.

Источники снимка:
- **обычные вкладки** — `Tab` (счётчик `evictedLines` в цикле обрезки `removeAt(0)`);
- **главная вкладка** — `TelnetClient` поверх `receivedData` (счётчик вытесненных
  строк в `appendToBuffer`; логику промпта `addLocalOutput`/`addToOutputRaw` НЕ
  мигрировали — см. подводный камень №11).

> Работаем в координатах **видимого (plain) текста** (`AnnotatedString.text`, ANSI
> уже разобран). Число строк в plain == в raw (escape-коды не добавляют `\n`),
> поэтому seq согласован; столбцы считаем в plain.

## 4. Модель скролла/раздвоения

**Единственный источник правды — `scrollbackScrollPx`** (пиксельный сдвиг скроллбэка)
в диапазоне `[0, maxScroll]`, где `maxScroll = contentHeight - viewport` (как у
обычного скроллбара).

Геометрия (всегда, не зависит от режима):
```
bottomPaneHeightPx = viewport * splitFraction      // живой хвост
topPaneHeightPx    = viewport - bottomPaneHeightPx  // скроллбэк
bottomScrollPx     = contentHeight - bottomPaneHeightPx   // хвост всегда у конца
maxScroll          = contentHeight - viewport
```

- **split (раздвоено)** ⟺ `scrollbackPx < maxScroll - lineHeight` (скроллбэк не у
  низа ⇒ есть разрыв с хвостом). Выводится прямо из позиции — НЕ отдельный флаг-режим.
- **При `scrollbackPx == maxScroll`** низ верхней панели стыкуется с верхом хвоста →
  виды непрерывны. Тогда рендерим ОДНО окно (иначе короткий контент дублируется —
  камень №8). Разделитель-линия рисуется только при split.
- `maxScroll` одинаков для одно- и двухпанельного режима → переход **бесшовный**
  (на границе оба показывают одно и то же), без прыжка.

`OutputScrollController` (чистый) хранит `followMode` (внизу ли) и `anchorSeq`,
возвращает цель `Bottom | ToLine(seq) | None`. Но **точную позицию** считает не он:

### Якорь — по символу, не по пикселю

При пользовательском скролле сохраняем якорь верхней видимой позиции как
**`(anchorSeq, anchorCol, anchorOffsetPx)`** (строка, столбец, суб-строчный сдвиг).
При ЛЮБОМ изменении (контент/высота вьюпорта) пересчитываем точный пиксель:

```
scrollbackPx = anchorToPx(layout, plainText, firstSeq, anchorSeq, anchorCol) + anchorOffsetPx
```

где `anchorToPx` — найти строку по `seq`, в её собственной разметке взять
`getLineTop(getLineForOffset(col))` и прибавить верх строки в стопке. Это держит
ОДИН И ТОТ ЖЕ контент наверху, что бы ни менялось (см. камни №4, №5, №7).
Если `followMode` — просто `scrollbackPx = maxScroll` (следуем за низом).

**Поиск переиспользует якорь:** переход к совпадению = выставить `anchorSeq` на
строку совпадения + `controller.jumpToLine(seq)`.

## 5. Выделение

Своя модель (`OutputSelection`), НЕ Compose `SelectionContainer` (камень №9):
- выделение = пара `(seq, col)` anchor/focus по **всему буферу**, не зависит от
  панелей → переживает раздвоение/схлопывание и «разрыв» между панелями;
- подсветка рисуется в `OutputCanvas` по строкам: для каждой строки диапазона —
  `getPathForRange` её разметки, сдвинутый на её верх (`pathForRange`);
- drag-жест и сброс по клику объединены в один `awaitEachGesture` (камень №9);
- копирование Ctrl+C/Cmd+C/Ctrl+Insert = `clipboard.setText(plain-подстрока)`.

## 6. Поиск

`OutputSearch` (чистый): находит все совпадения (подстрока/regex, регистр), хранит
текущий индекс, next/prev по кругу, переживает обновление контента. `OutputSearchBar`
(Ctrl+F) — поле, счётчик `n/m`, тумблеры `Aa`/`.*`, навигация Enter/Shift+Enter/F3.
Подсветка совпадений — отдельные пути в `OutputCanvas` (все — жёлтым, текущее —
оранжевым). Переход к совпадению — через якорь (см. выше).

## 7. Рендеринг (ключевое для производительности и багов)

- `AnnotatedString` парсится один раз на окно (`AnsiParser`) и режется на
  логические строки (`splitLines`); **разметка — у каждой строки своя**.
  `LineLayoutCache` хранит её по абсолютному `seq` и размечает заново только
  строки, чьё содержимое (текст и отрезки) изменилось — в норме одну, промпт.
  Место строки по вертикали — сумма высот строк выше (`LineStack`). Все панели
  читают одно окно (`MeasuredWindow`), без двойного measure.
- Любой перевод «пиксель ↔ символ» — два шага: найти строку (по `y` или по
  `seq`), затем спросить её разметку (`anchorToPx`, `pxToAnchor`,
  `pointToSelPoint`, `pathForRange`, `pathForOffsets`).
- `OutputCanvas` рисует через `Canvas`/`drawText` только строки, попавшие во
  вьюпорт, каждую на своей высоте; подсветки — готовыми путями.
- **Размер берётся через `onSizeChanged`, НЕ `BoxWithConstraints`** (камень №1).
- **Скролл и ревизии выделения/поиска читаются в фазе draw** (`scrollProvider()`,
  `revisionState.value`) → Canvas перерисовывается при их изменении БЕЗ рекомпозиции
  (камни №1, №10).
- Лимит парсинга — последние ~1000 строк больших буферов (`firstSeq` корректируется
  на срезанные).

## 8. Где живёт состояние

`OutputViewHolder` (по экземпляру на вкладку) хранится в `ClientState`
(`outputViewHolder(tabId)`), а НЕ в `remember` внутри `OutputPanel`. Причина: при
переключении верхнеуровневых вкладок `MainWindow` пересоздаёт контент через
`when(selectedTabId)`, и `remember` бы потерялся. Поэтому позиция/режим/выделение/
поиск/доля разделителя — всё в holder и переживает переключения.

## 9. Кросс-платформенность

Чистая логика и рендер-ядро — на multiplatform-API (`TextMeasurer`, `Canvas`,
`drawText`, `getPathForRange`, `pointerInput`, `LocalClipboardManager`): при будущей
миграции на KMP уедут в `commonMain`. Desktop-специфика (колесо, Ctrl-хоткеи,
скроллбар, mouse-drag-select) изолирована в слое ввода; на Android её заменит свой
жест-слой. Сейчас проект — чистый JVM/Desktop (не KMP).

## Подводные камни

> Большинство багов этой подсистемы — в Compose-склейке, а не в логике. Вот они.

### №1. `BoxWithConstraints` — ленивая рекомпозиция (SubcomposeLayout)
`BoxWithConstraints` использует `SubcomposeLayout`, контент которого рекомпозируется
**лениво, только при перемере**. Изменения состояния, не влияющие на размер (скролл,
выделение), НЕ перерисовывали содержимое на «статичных» вкладках. На главной
«работало» лишь потому, что туда периодически капал текст и форсил рекомпозицию.
**Решение:** размер через `Modifier.onSizeChanged` (весь рендер в обычной композиции)
+ читать динамику в фазе draw.

### №2. `key(tabId)` — иначе поддерево показывает чужую вкладку
Без `key(activeTab.id)` вокруг `ScrollbackOutputView` Compose переиспользует
composable по тому же месту при переключении под-вкладок, и при ненадёжной
рекомпозиции рисуется ПРЕДЫДУЩАЯ вкладка (симптом: «выделение на Ассистенте
появлялось на Главной»). **Решение:** `key(tabId)` → свежее поддерево на вкладку.
Минус: пересоздание сбрасывает локальные `remember` (но holder в ClientState живёт).

### №3. Устаревшие колбэки/значения в `pointerInput(Unit)`
`pointerInput(Unit)` НЕ перезапускается при рекомпозиции, поэтому его лямбды
**захватывают значения первой композиции навсегда**. Скроллбар звал устаревший
`onScrollTo` (со старым `maxScroll`=162 при актуальном 366) → ползунок мапил на
неверный диапазон → скачок к низу, follow залипал. То же — `scrollProvider` (захват
точки) и `splitFraction` разделителя. **Решение:** всё, что меняется, оборачивать в
`rememberUpdatedState` и звать `.value` внутри жеста; либо локальный аккумулятор от
старта drag (как у разделителя). Это объясняло, почему **колесо работало, а ползунок
нет** — обработчик колеса (`onPointerEvent`) пересоздаётся каждую рекомпозицию.

**Что именно устаревает, а что нет** (проверено обходом всех жестов клиента):

| В жесте используется | Актуально? |
|---|---|
| `val x by remember { mutableStateOf(...) }` | да — делегат читает `.value` при обращении |
| `val x by clientState.foo.collectAsState()` | да — тот же механизм |
| обычный `val` (вычисленный: `maxScroll`, `lineHeightPx`) | **нет** — замирает на первой композиции |
| параметр composable (`splitFraction`) | **нет** |
| лямбда-параметр (`onScrollTo`, `onSplitFractionChange`, `collapse`) | **нет** |

Поэтому в других панелях (карта, миникарта, статус) той же ошибки нет: там
перетаскивание работает со state-делегатами. А в панели вывода почти все
величины — вычисленные, и на этих граблях успели потоптаться трижды:
ползунок скроллбара, разделитель и кнопка «вниз» (она возвращала не к концу
лога, а к позиции, где пользователь начал читать: `maxScroll` был захвачен
в момент появления кнопки).

Исключение, сделанное сознательно: геометрия ползунка (`track`, `thumb`,
`denom`) фиксируется на время перетаскивания. Пересчитывать её при росте лога
нельзя — ползунок будет уползать из-под курсора; позиция и предел при этом
берутся свежие.

### №4. Пиксельный абсолютный скролл хрупок при изменении высот
`scrollbackPx` в пикселях указывает «не туда», как только меняется высота контента
или вьюпорта. **Решение:** якорить по символу `(seq, col, offsetPx)` и пересчитывать
пиксель в новом layout (см. §4).

### №5. Высота вьюпорта скачет (панель подключения)
`maxScroll = contentHeight - viewport`. При логине/реконнекте сверху появляется/
исчезает панель «Профиль подключения» → высота области вывода меняется → `maxScroll`
скачет (наблюдали 162↔366) → пиксельный скролл ломается. Якорь по символу (камень №4)
это лечит: пере-привязка держит контент. Диагностируется логом `vp=` отдельно от `ch=`.

### №6. `atBottom` / залипание follow
`atBottom` считался против НЕАКТУАЛЬНОГО `maxScroll` (из-за камня №3) → даже скролл
вверх засчитывался «у низа» → `followMode` не выключался → новый текст прижимал к
низу (сброс позиции). У самого низа дополнительно **защёлкиваем точно в `maxScroll`**,
чтобы достичь низа и схлопнуться.

### №7. Дрожь на переносах строк (seq↔px round-trip)
`topSeqAt(px)→seqToTopPx(seq)` терял точность: `seqToTopPx` защёлкивал к началу
ЛОГИЧЕСКОЙ строки, а длинные строки переносятся на несколько визуальных → при новом
тексте позицию «подравнивало» вверх. **Решение:** якорь с суб-строчным `anchorOffsetPx`
и `anchorToPx` через `getLineForOffset` (точная визуальная строка).

### №8. Дублирование на коротком контенте
«Всегда две панели» дублирует текст, когда контент короче вьюпорта (обе панели
показывают одно). **Решение:** две панели только при реальном раздвоении; при
`scrollbackPx == maxScroll` (внизу) ИЛИ когда контент помещается — ОДНО окно.

### №9. Конфликты жестов и выделение «не теми» жестами
- Tap (сброс выделения) и drag (выделение) раздельными `pointerInput` конфликтовали:
  после короткого drag tap-детектор срабатывал и сбрасывал свежее выделение (хуже на
  коротких вкладках). **Решение:** объединить в один `awaitEachGesture`.
- Разделитель/скроллбар ВНУТРИ области жеста выделения → их перетаскивание выделяло
  текст. **Решение:** держать их СОСЕДЯМИ вне жеста выделения (область ввода сужена
  под скроллбар через `padding(end)`).
- `SelectionContainer` не умеет переживать смену дерева «один Text ↔ два Text» и
  «разрыв» панелей → отсюда своя модель выделения по `(seq,col)`.

### №10. Перерисовка без рекомпозиции — через фазу draw
Когда рекомпозиция ненадёжна, читай динамические величины (`scrollPx`, ревизии
подсветки) ПРЯМО в лямбде `Canvas`/`drawBehind` — фаза draw наблюдает snapshot-чтения
и перерисовывает слой при их изменении, минуя композицию. Так сделаны
`scrollProvider`, `revisionState`, `searchRevisionState`.

### №11. Главная вкладка ≠ строковая модель Tab
Главная рендерит `TelnetClient.receivedData` (char-буфер, обрезка по байтам, строка-
сентинел `[Buffer cleared]`), а не `Tab.lines`. Логика промпта (`addLocalOutput`/
`addToOutputRaw`) вставляет текст ПЕРЕД незавершённой строкой-промптом прямо в
`receivedData`. Её НЕ мигрировали (риск регрессий промпта) — вместо этого добавили
счётчик вытесненных строк в `TelnetClient` для seq. Если будешь унифицировать —
перенеси логику промпта в строковую модель.

### №12. ANSI и координаты
ANSI-состояние (цвет) переносится между строками; парсим весь буфер сразу (per-line
парсинг потерял бы перенос). Все offset/выделение/поиск — в координатах plain-текста
(`AnnotatedString.text`), число строк plain==raw, столбцы в plain. Режем на строки
уже размеченный результат: `AnnotatedString.subSequence` сохраняет отрезки.

### №13. Разметка стоит по отрезкам, не по символам — и не переживает обновление
Окно размечалось одним `TextLayoutResult` на каждое обновление: тысяча строк
игры — 84 мс на каждый пришедший кусок, при том что 999 строк те же, что секунду
назад. Те же строки **без цветов** укладывались в кадр: цена — в стилевых
прогонах Skia, по одному на цветной отрезок, а их по несколько на строку.
Отсюда задержка при ходьбе (#19): эхо команды и комната — два обновления,
на слабой машине по 300 мс. **Решение:** разметка по строкам с кэшем по `seq`
(`LineLayoutCache`); заново размечается только изменившееся. После починки
разметка не вылезает за 5 мс; заметным остался разбор ANSI всего окна
(5–14 мс на ~1000 строк) — следующий кандидат, если окно расти будет.

## Тестирование

Чистая логика покрыта юнитами и НЕ требует ручной проверки:
`OutputScrollControllerTest`, `BufferOffsetsTest`, `OutputSelectionTest`,
`OutputSearchTest`, `LineStackTest`, `LineLayoutCacheTest`, seq в `TabTest`. Непокрываемый зазор — пиксельная Compose-склейка
(рекомпозиция/жесты/измерения): её проверяют вручную (`./gradlew run`). Именно там
жили все баги — поэтому склейка тонкая, а грабли выше задокументированы.

Сборка/тесты: см. вспомогательную заметку о JAVA_HOME + Windows-ROOT trust store.

## Точки расширения

- **Новый вид подсветки** (напр., триггерная) — ещё пара путей в `OutputCanvas` +
  своя ревизия, читаемая в draw.
- **Переход к строке/совпадению** — `controller.jumpToLine(seq)` + якорь.
- **Android** — заменить desktop-слой ввода (`DesktopOutputInput`) на жест-слой
  (long-press + ручки + тулбар, touch-скролл), ядро/логика переиспользуются.
